## Controls found

- Frontend uses `VITE_SUPABASE_PUBLISHABLE_KEY`, not service-role configuration (`app/supabase.ts:3–6`). Authentication checks precede protected operations; service-role callers scope user/trip/environment. Public search intentionally differs from private booking access.
- `supabase/schema.sql:14–23` uses `auth.uid()` on trip SELECT/INSERT/UPDATE. `liteapi-checkout.sql:16–30` denies browser table access and restricts claim transitions to service_role; financial/support/AI RPC scripts revoke execute from public/anon/authenticated as appropriate. Review complete ordered migrations before inferring grants from a single file.
- `worker/payments.js:6–17,29–36` verifies amount/currency/order/signature and rechecks status. Hotel checkout binds selection to user/trip/room dates, serializes state changes and encrypts payload; fixture tests cover wrong totals/URLs/consent and isolation. This is evidence of controls, not live financial success.
- `worker/google-routes.js` validates fixed providers, auth and transactional usage budgets. AI uses authenticated quota reservation/completion and a bounded provider deadline. Viator uses fixed hosts and a limiter. Support uses a dedicated bot, webhook secret/private-chat allowlist, sensitive-message rejection and replay-aware outbox, separate from local agent tools.
- Supplier URLs/quotes and official-admission sources are constrained. Logs examined use fixed phase/error categories rather than credential/header dumps. The bounded static scan found no hardcoded secret pattern; live logs/screenshots/history were not inspected.

## New-feature threat model and required tests

1. SSRF: parse URLs, exact host/path/provider-ID allowlists, HTTPS only, reject credentials/ports/IP literals/encoded host tricks/local/reserved IPs. Deny generic fetch and arbitrary redirects; short links initially require canonical URL. Fixed official endpoints receive only validated IDs. Validate all redirect hops and DNS/egress if remote retrieval is later permitted. Never let the model supply an unrestricted fetch target or send user tokens to third-party URLs.
2. Uploads: authentication first; signed owner-scoped bounded grants; random object keys; sniff format and count streamed bytes; trusted duration/track inspection; reject polyglots, malformed containers, excessive resolution/duration, compressed bombs and remote playlist references. Sandbox media tooling, use argument arrays, no network, CPU/memory/time limits; no executable uploads or shell interpolation.
3. Privacy: explicit right-to-process/provider-sharing consent; avoid faces/voices of others, precise GPS/EXIF and private overlays; strip unnecessary metadata. Private storage, TTL/deletion/cancel cleanup and minimal derived records. Meta Files do not auto-expire. Contributor training mode must not be selected silently.
4. Prompt/tool injection: captions/OCR/transcripts/pages are data, not authority. Strict tool schema and tool registry; no SQL/shell/payment/message tools. Validate tool results and semantic place IDs before using them.
5. Authorization/concurrency: owner binding on every job/file/result; A cannot enumerate/read/cancel B; upload grant cannot change object key/size/user; stale revisions fail; idempotency and budget reservations serialize duplicate starts; no partial job grants a pass or marks paid.
6. Logging: no media bytes, transcripts, exact private URLs, provider file IDs, headers, tokens or raw exception bodies. Safe error code/phase/timing/usage only. Public attribution/source links must not contain secrets.

All are requirements for future implementation. None of these attack payloads was sent to production. OWNER_ACTION_REQUIRED items and sequencing are listed separately; fixing findings is not implicitly authorized by this audit-only brief.
